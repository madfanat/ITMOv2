# US-03: независимый черновик команды логики

Статус: исходное предложение до согласования общего контракта и генерации кода.
Автор: отдельный агент команды логики. Дата: 2026-10-28.

## Источники и границы

Третий сценарий `practices/practice_01/product_management.md` — «Таймаут LLM»:
при ответе провайдера дольше 10 секунд API возвращает контролируемую ошибку.
Формулировка User Story: как разработчик/CI, я хочу получить понятный отказ,
если LLM не ответила за 10 секунд, чтобы запрос не зависал и его можно было повторить.
Исходные правила: SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1
из `practices/practice_01/context.md`.

Границы: API ревью, отменяемый асинхронный провайдер, локальный детерминированный
стенд. Нет очереди, автоматических повторов, БД, изменений PR, подключения GitHub
или обязательных платных ключей. Сквозной UI согласуется с отдельной командой.

## Предлагаемое поведение

1. `POST /api/reviews`, JSON `{ "diff": "..." }`. Допускается только непустая
   строка; отсутствие поля, null, неверный тип, пустота/пробелы и лишние поля → 422.
   Лимит API-1 измеряется в символах Unicode: ровно 20000 разрешено, 20001 → 413.
   Проверки происходят до вызова провайдера.
2. До вызова LLM замаскировать распознаваемые пароли, токены и PEM private keys.
   Проверка SEC-1 должна наблюдать фактический prompt у spy-провайдера.
   Конкретные поддерживаемые шаблоны описать и проверить: эвристика не обещает
   распознать произвольный секрет без известного шаблона.
3. Ожидать `await provider.generate(masked_prompt)` максимум 10.0 секунд.
   Таймаут отменяет coroutine; провайдер обязан поддерживать cooperative cancellation.
   Не запускать блокирующий вызов в thread pool, который продолжит работу после ответа.
   При отключении клиента/отмене запроса также не поглощать `CancelledError`.
4. Успех → 200, ровно `summary`, `risks`, `checks`; риск содержит `file`, `line`,
   `evidence`, `risk`, число рисков ≤3. Проверить типы результата до ответа.
   Невалидный результат/отказ провайдера → контролируемый 502 без исходного исключения.
   По QA-1 демонстрационный провайдер возвращает `risks: []`, если нет доказательств.
5. Таймаут → HTTP 504; предварительный вариант тела:
   `{ "error": { "code": "llm_timeout", "message": "LLM не ответила за 10 секунд. Повторите запрос." }, "request_id": "..." }`.
   Ошибки 413/422/502 имеют ту же внешнюю оболочку и стабильные коды.
6. `GET /health` → 200 `{ "status": "ok" }`, в том числе во время ожидания LLM.
   Логировать только `request_id`, `duration`, `status`; содержимое diff, ответа
   модели и текста исключения не попадёт в application/access logs. Ошибки
   валидации не должны отражать исходный ввод в JSON.

## Детерминированный локальный стенд

Внедряемый DemoProvider: normal отвечает быстро валидным фиксированным JSON;
slow спит более 10 секунд и регистрирует отмену в тесте; error возбуждает
исключение; invalid возвращает несоответствующую схему. Реальные сетевые вызовы
не нужны. В тестах дедлайн можно внедрить как 0.05 секунд, но один сквозной
тест обязан проверить реальные 10 секунд (например, допустимое окно 9.5–12.0 с).

Предложение для UI: режим выбирается необязательным заголовком
`X-Demo-Scenario: normal|slow|error|invalid` только в явно включённом demo режиме;
поле `diff` и production-контракт остаются прежними. Другая возможность — разные
конфигурации запуска. Решить с UI до кода, чтобы не добавить скрытый управляющий
текст в diff.

## Критерии и проверки

| ID | Given / When / Then | Проверка |
|---|---|---|
| L-01 | Валидный diff / POST / 200 с OUT-1 | HTTP integration, проверка схемы |
| L-02 | Медленный cancellable provider / дедлайн / 504 и coroutine отменена | Unit со spy отмены + HTTP с реальными 10 с |
| L-03 | После 504 / повтор normal / 200 | E2E retry, отсутствие старого результата |
| L-04 | 20000 и 20001 Unicode символов / POST / 200 и 413 | Граничная HTTP проверка, provider не вызван при отказе |
| L-05 | Пропуск/null/число/пустота/лишние поля / POST / 422 без отражения diff | Параметризованный integration |
| L-06 | Пароль/токен/PEM / ревью / секрет отсутствует в prompt и logs | Spy + захват логов |
| L-07 | Исключение или сломанный ответ LLM / POST / безопасный 502 | Injection провайдеров |
| L-08 | Запрос LLM ожидается / health / быстрый 200 | Конкурентный HTTP test |
| L-09 | Любой запрос / лог / только разрешённые metadata | Захват log records |

## Вопросы для согласования с UI

- Принимает ли UI 504 как отдельное состояние `timeout`, а 502 как `error`?
- Нужен ли `request_id` в теле успешного ответа? Логика предлагает заголовок
  `X-Request-ID` для всех ответов, чтобы сохранить OUT-1 без расширения тела.
- Как выбирать demo-сценарий: заголовок в demo режиме либо отдельный запуск?
- Какой timeout у браузера? Он должен быть больше серверных 10 секунд, иначе
  UI потеряет контролируемый 504. Предложение: 15 секунд для транспортного сбоя.

Это предложения агента; человеческая приёмка не зафиксирована.
