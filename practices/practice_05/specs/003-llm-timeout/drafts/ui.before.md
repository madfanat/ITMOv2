# UI specification — draft before contract alignment

Статус: самостоятельный черновик команды UI; реализация ещё не начата.
Дата: 2026-10-28. Процесс: Spec Kit, этап Specify.

## Источник и границы

US-03 соответствует третьему сценарию в
`practices/practice_01/product_management.md`: если LLM отвечает дольше
10 секунд, пользователь получает контролируемую ошибку. Правила REL-1,
API-1, OUT-1, SEC-1, OBS-1 и SCOPE-1 взяты из
`practices/practice_01/context.md`.

Как разработчик, отправляющий diff на AI-ревью, я хочу понимать, что
запрос завершился таймаутом, и повторить его без повторного ввода diff.

UI не управляет таймаутом провайдера и не выполняет автоматических
повторов. Выбор реального LLM, хранение истории, GitHub и авторизация
не входят в изменение.

## Экран и действия

Один экран `/`: заголовок «AI review», подписанное многострочное поле
«Diff», счётчик символов, кнопка «Проверить», область статуса и результата.
Ограничение поля — 20 000 символов Unicode; пробельный diff не отправляется.
Введённый текст сохраняется в памяти страницы при любом исходе; в
localStorage и журнал браузера он не записывается.

Для воспроизводимого локального демо нужен явно обозначенный режим
«Успех / Медленный LLM»; способ передачи режима требует согласования.

| Состояние | Видимое поведение | Доступные действия |
|---|---|---|
| idle | Поле и инструкция; пустой результат | Редактирование; отправка непустого допустимого diff |
| loading | «Выполняется ревью…»; старый результат скрыт | Повторная отправка заблокирована до ответа |
| success | Summary, список risks (не более трёх), checks | Новый запрос или редактирование |
| timeout | «LLM не ответил за 10 секунд. Попробуйте ещё раз.»; старого успешного результата нет | «Повторить» с сохранённым diff |
| error | Понятное сообщение валидации, сети или сервиса; старый результат скрыт | Исправление ввода либо повтор |

## Предлагаемый исходный контракт

- Запрос: `POST /api/reviews`, JSON `{"diff":"..."}`.
- Успех: HTTP 200, `{"summary":"...","risks":[],"checks":[]}`.
- Таймаут: предлагается HTTP 504 и `{"error":"llm_timeout","message":"LLM не ответил за 10 секунд"}`.
- Невалидный JSON / отсутствующий diff / неверный тип: HTTP 422.
- Более 20 000 символов: HTTP 413.
- Провайдер недоступен или вернул некорректный ответ: предлагается HTTP 502.
- Сетевая ошибка браузера показывается отдельно от таймаута LLM.

UI доверяет серверному статусу 504, а не собственному таймеру 10 секунд:
сетевые накладные расходы не должны превращать корректный серверный
ответ в ошибку браузера. Время запроса можно показывать для демонстрации,
но оно не заменяет контракт.

## Условия приёмки

1. **UI-AC1.** Given допустимый diff, when пользователь отправляет его,
   then видит loading и не может создать дубликат до завершения запроса.
2. **UI-AC2.** Given ответ 200, when запрос завершён, then отображаются
   summary, risks и checks; произвольный текст ответа выводится как текст,
   а не исполняемый HTML.
3. **UI-AC3.** Given LLM не завершился за 10 секунд, when сервер вернул
   согласованный ответ таймаута, then видны отдельное состояние timeout,
   сообщение о 10 секундах и кнопка повтора; diff сохранён.
4. **UI-AC4.** Given timeout, when пользователь повторяет запрос в режиме
   успеха, then получает результат без перезагрузки страницы.
5. **UI-AC5.** Given невалидный или слишком длинный diff, when пользователь
   пытается отправить его, then видит понятную ошибку; сервер также
   сохраняет независимую валидацию входа.

## Доступность

У textarea есть связанный label; все кнопки работают с клавиатуры.
Статус объявляется через `aria-live`, ошибка через `role="alert"`;
loading отмечается `aria-busy`. Состояния различаются текстом, а не только
цветом. Не отключать textarea навсегда после ошибки; фокус после повтора
остаётся предсказуемым.

## Вопросы к команде логики до реализации

1. Будет ли ошибка плоской, как предложено выше, или единым envelope
   `error.code / error.message / request_id` для всех кодов?
2. Как безопасно включать медленный локальный провайдер: конфигурацией
   сервиса, отдельным демо-запуском или явным полем запроса?
3. Гарантируется ли освобождение ресурсов провайдера после таймаута и
   успешный следующий запрос? UI не должен обещать это без проверки.
4. Какой стабильный формат имеет 422? UI нужен общий fallback, чтобы
   внутренние поля Pydantic не становились пользовательским сообщением.

Эти вопросы не обозначают согласование человеком. Итоговая версия UI
должна быть обновлена после общего контракта и до генерации кода.
