# Практика 7.1: ассистент для код-ревью в n8n

На занятии вы разворачиваете n8n, разбираете устройство нод и AI Agent, импортируете базовый сценарий ассистента для ревью и дорабатываете его: основной флоу запускается только при открытии PR, а ревью можно вызвать комментарием `/make_ai_review`.

Базовый JSON-сценарий: [gist](https://gist.github.com/abramov-ks/04bcedd21dc1b29487e716482cef0a3d). Токен GitHub создаётся в [настройках](https://github.com/settings/tokens). Подробности по доступу к n8n и VseLLM — в презентации.

## Домашняя работа: вторая модель, дедупликация и точечные комментарии

Продолжайте сценарий, собранный на занятии. Сделанное на занятии засчитывается. Шаги идут от простого к сложному и выполняются по порядку: каждый следующий опирается на предыдущий.

1. **Добавьте команду `/make_other_ai_review`.** Команда запускает ревью с помощью второй модели — любой, отличной от основной — и публикует результат в PR.
2. **Подключите Data Table.** Самостоятельно разберитесь с механизмом Data Table в n8n и встройте его в сценарий: сохраняйте id PR, для которых уже сделано ревью.
3. **Исключите повторные запуски.** При новом комментарии `/make_ai_review` к PR, который уже есть в таблице, ревью не должно запускаться повторно.
4. **Задание «со звёздочкой»: точечные комментарии.** Доработайте сценарий так, чтобы комментарии публиковались не ко всему diff PR, а точечно — к каждому блоку изменённого кода.

## Что подготовить для сдачи

- Экспорт доработанного сценария в JSON.
- Ссылку на тестовый PR с комментариями ассистента.
- Подтверждение каждого выполненного шага: скриншоты вкладки Executions и, для шагов 2–3, содержимое Data Table.

## Что студент показывает ревьюверу

- Как устроен выбор модели для `/make_other_ai_review` и чем отличаются результаты двух моделей.
- Где хранится состояние и как сценарий решает, запускать ревью или нет.
- Что происходит при повторном `/make_ai_review` к тому же PR.
- Для задания «со звёздочкой» — как diff разбивается на блоки и как комментарии привязываются к строкам.

Наличие ноды в сценарии само по себе не подтверждает её работу — приложите подтверждения реальных запусков.

## Оценка, 12 баллов

Каждый критерий бинарный: баллы начисляются целиком, если критерий выполнен и подтверждён реальным запуском, иначе — 0. Критерии проверяются по порядку: баллы за следующий критерий начисляются, только если засчитаны все предыдущие.

| # | Критерий | Баллы |
|---|---|---:|
| 1 | Команда `/make_other_ai_review` запускает ревью второй моделью, результат опубликован в тестовом PR | 2 |
| 2 | Data Table создана, id PR сохраняется в неё после ревью — видно в содержимом таблицы | 2 |
| 3 | Повторный `/make_ai_review` к уже проверенному PR не запускает ревью — видно в Executions | 3 |
| 4 | Комментарии публикуются точечно, к каждому блоку изменённого кода — видно в тестовом PR | 5 |
| | **Итого** | **12** |

## Учебный n8n

[Опубликованный workflow](https://n8n-itmo.cyrweb.ru/workflow/o9UozImE5ZHsJwOj) принимает события прямо от GitHub. Основная модель `openai/gpt-4.1-mini` запускается при открытии PR и по `/make_ai_review` для непроверенного PR. `/make_other_ai_review` запускает `google/gemini-2.5-flash`. Обе модели вызываются через действующий VseLLM credential на учебном шлюзе `litellm.data-light.ru`.

Для повторного развёртывания импортируйте [workflow.course.json](workflow.course.json). Создайте в проекте Data Table по схеме ниже. Назначьте GitHub API credential триггеру и четырём HTTP-нодам GitHub. Ноде `Review blocks with VseLLM` назначьте credential типа **OpenAI API** с ключом VseLLM для учебного шлюза и Base URL `https://litellm.data-light.ru`. Укажите репозиторий в триггере и опубликуйте сценарий. Учебный экземпляр уже настроен для демонстрации.

## Локальный запуск с Ollama

Импортируйте [workflow.json](workflow.json) в n8n 2.40.0. Сценарий принимает события GitHub, передаёт изменённые блоки в Ollama и публикует один GitHub review с отдельным комментарием для каждого блока.

1. Запустите Ollama на хосте n8n и загрузите обе модели. Если процессы размещены на разных хостах, укажите доступный адрес в ноде `Review blocks with Ollama`.

   ```sh
   OLLAMA_HOST=127.0.0.1:11571 ollama serve
   ```

   ```sh
   OLLAMA_HOST=127.0.0.1:11571 ollama pull qwen3.5:9b
   OLLAMA_HOST=127.0.0.1:11571 ollama pull qwen3.5:4b
   ```

2. В проекте n8n создайте Data Table `practice_071_reviewed_prs`. Добавьте текстовые столбцы `pr_id`, `repository`, `last_model`, `review_id` и числовой столбец `pr_number`. Обе ноды Data Table находят таблицу по имени. [Документация n8n Data Table](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.datatable/).
3. Назначьте credential типа **GitHub API** триггеру `GitHub PR and comments` и четырём HTTP-нодам GitHub. В триггере укажите владельца и имя репозитория. Credential должен иметь доступ к PR на чтение и запись, а для регистрации триггера нужны права на управление webhook. [Документация n8n GitHub Trigger](https://docs.n8n.io/integrations/builtin/trigger-nodes/n8n-nodes-base.githubtrigger/).
4. Для автоматической доставки событий задайте `N8N_WEBHOOK_URL` с HTTPS-адресом webhook, доступным GitHub. На выделенном экземпляре n8n задайте `N8N_CONCURRENCY_PRODUCTION_LIMIT=1`, чтобы два одновременных события об одном PR проходили проверку и запись последовательно. Опубликуйте workflow. [Документация n8n по управлению конкурентностью](https://docs.n8n.io/hosting/scaling/concurrency-control/).
5. Откройте PR с текстовыми изменениями. После первого ревью оставьте `/make_other_ai_review` для второй модели и `/make_ai_review` для проверки пропуска повторного запуска.

Data Table хранит глобальный GitHub `pull_request.id` и идентификатор последнего опубликованного ревью. Основная ветка при существующем ID завершается в `Skip review`, а команду второй модели можно вызвать на уже проверенном PR. Если GitHub принял ревью, но n8n исчерпал повторы записи в таблицу, восстановите строку по опубликованному ревью перед повторным запуском.

Сценарий останавливает публикацию, если GitHub вернул неполный текстовый патч или если изменился SHA базовой или головной ветки. В блоке с добавлениями якорем служит последняя добавленная строка `RIGHT`. Для блока, содержащего только удаления, используется последняя удалённая строка `LEFT`. [GitHub REST API для ревью PR](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request).
